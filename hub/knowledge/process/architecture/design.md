# 架構設計的規則

架構設計先理解問題，再產生多個候選方案，最後才收斂與細化。跳過問題理解直接畫圖，是架構設計最常見的錯誤。

## 輸入

| 必要性 | 輸入 | 缺少時 |
|---|---|---|
| 必要 | 需求描述（PRD、user story 或口述） | 暫停，請使用者提供 |
| 重要 | 規模數據：用戶量、流量、資料量、成長預期 | 以假設值繼續，並標明是假設 |
| 重要 | 約束：時程、預算、團隊規模與技能、既有技術棧、合規 | 主動詢問 |
| 選配 | 既有系統的資料 | 改造既有系統時，先依[現有架構盤點](kb:process/999284)重建現況 |

改造既有系統時，現況盤點是情境分析的前提；沒有現況理解的改造設計等於盲改。

## 設計簡報

情境分析的產出是一頁設計簡報，包含：

- **業務目標**：系統成功的定義，連到可度量的業務指標。
- **範圍邊界**：明確的 in-scope 與 out-of-scope。
- **利害關係人與關注點**：業務、維運、資安、財務各自在乎什麼。
- **硬性約束**：不可協商的限制，例如合規、時程、預算、指定技術。
- **關鍵假設**：所有自行推定的前提，逐條列出。

設計簡報偏了，後續全部跟著偏，因此假設清單必須經使用者確認。

## 候選方案

- 產生 2 到 3 個**結構上不同**的候選方案：不同的架構風格或拆分策略，而不是同一方案的參數微調。
- 候選方案沿最重要的品質屬性展開（例如優先可用性的多活方案與優先簡單性的單區方案），或沿演進策略展開（例如模組化單體、直接微服務、絞殺者模式漸進改造）。
- 最簡單的可行方案永遠是候選之一，作為其他方案複雜度的對照基準。

每個候選方案以下列格式描述：

```markdown
### 候選 {X}：{一句話定位}
- 結構摘要：主要組件與互動方式
- 最適合的情境：什麼條件下它是對的
- 主要優勢：對哪些驅動屬性有利
- 主要代價：犧牲了什麼（必填）
- 演進路徑：未來如何成長或轉型
```

## 評選

- 以[品質屬性分析](kb:process/8796e4)中業務價值與技術風險皆為高的場景，逐一檢驗每個候選方案，逐格寫出如何滿足或為何不滿足，不打抽象分數。
- 另外比較交付時程、團隊能力匹配與成本量級。
- 以 Y-statement 給出推薦、理由與接受的代價；選定方案由使用者決定，並記錄為 ADR。

## 細化

選定方案依序展開：

1. 依[C4 架構圖](kb:process/4dcc39)產出 L1 與 L2，高風險容器加畫 L3。
2. 每個容器的技術：已有組織標準的直接沿用並標明；需要評估的依[技術選型評估](kb:process/d90b9b)；屬於單向門的依[重大技術決策的規則](kb:process/8b58b1)獨立處理。
3. 為最重要或最危險的 2 到 3 個流程畫 sequence diagram，包含失敗路徑。
4. 資料概觀：核心實體、資料擁有權（哪個服務擁有哪些資料）、一致性策略。

細化後依[架構風險評估](kb:process/d923ae)稽核風險；等級為高的風險閉環之前，不進入文件產出。風險緩解改動了架構時，回頭更新架構圖。

## 交付

- 至少為下列決策撰寫 ADR：架構風格的選擇、每個重大技術選型、重大的風險接受。
- 架構設計文件預設以 Markdown 交付；組織有既定的文件範本時，依範本填入對應章節。
- 交付前確認：
  - 每個業務價值與技術風險皆為高的場景，都能在設計中找到對應的機制。
  - 圖、文件與 ADR 三者一致。
  - 所有假設都已確認或標明。
  - 等級為高的風險全部閉環。
  - 落選方案與落選理由已保存。
