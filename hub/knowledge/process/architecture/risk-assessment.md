# 架構風險評估

風險評估的產出不是風險清單，而是已閉環的高風險，以及有負責人的中低風險。

## 畫布

以 C4 L2 為畫布，每個風險定位到具體的元素或連線。「系統可能會掛」不合格，「訂單 API 對金流的同步呼叫在金流逾時時會耗盡連線池」才合格。還沒有架構圖時，先依[C4 架構圖](kb:process/4dcc39)產出。

## 多視角掃描

三個視角逐一掃過，不跳過。識別階段寧可誤報，不可漏報，評級時才收斂。

**Well-Architected 六支柱**：

| 支柱 | 典型提問 |
|---|---|
| 營運卓越 | 部署如何回滾，監控告警涵蓋關鍵路徑嗎，on-call 能自主排障嗎 |
| 安全 | 認證授權的邊界在哪，敏感資料在傳輸與靜態時是否加密，密鑰如何管理 |
| 可靠性 | 每個相依故障時會怎樣，有無重試、退避、斷路器，RTO 與 RPO 定了嗎 |
| 效能效率 | 瓶頸在哪個元素，快取策略為何，資料量成長十倍還撐得住嗎 |
| 成本最佳化 | 峰谷之間的資源策略，有無成本爆炸的路徑（例如沒有上限的 fan-out） |
| 永續 | 資源利用率，是否過度佈建 |

**常見架構風險**：

- **單點故障**：任何只有一個的東西，包括實例、AZ、憑證，以及唯一懂系統的人。
- **同步耦合鏈**：A 到 B 到 C 的同步呼叫鏈造成級聯故障與延遲疊加。
- **資料一致性**：跨服務交易、雙寫、事件與狀態不同步、缺乏冪等性。
- **容量假設**：寫死在設計裡的成長假設，例如分區鍵、單表、單佇列。
- **外部依賴**：第三方 API 的配額、SLA、棄用政策與費率變更。
- **部署與變更**：不可回滾的 migration、一次性切換、缺乏 feature flag。
- **演進阻力**：改一個需求要動幾個服務，測試環境能否重現生產拓撲。

**歷史事故**：逐條比對組織的 P0、P1 事故，確認同類模式是否在本架構重現；沒有紀錄時，詢問使用者過去一年最痛的三次事故。

## 評級

等級 = 機率 × 影響：

| | 影響低（1） | 影響中（2） | 影響高（3） |
|---|---|---|---|
| **機率高（3）** | 3 中 | 6 高 | 9 高 |
| **機率中（2）** | 2 低 | 4 中 | 6 高 |
| **機率低（1）** | 1 低 | 2 低 | 3 中 |

- 影響以對驅動屬性與業務的傷害判斷；資料遺失、營收中斷、合規罰則為高。
- 機率以一年內發生的可能性粗估；有歷史事故佐證的直接列為高。
- 評級有爭議時取較高等級，並註記分歧。
- 已經發生的是問題（issue），直接進修復流程，不列入風險登錄表。

## 風險登錄表

| 欄位 | 說明 |
|---|---|
| ID | R-001 起編 |
| 風險描述 | 定位到元素或連線，寫出觸發條件與後果 |
| 類別 | 支柱或風險類別 |
| 機率、影響、等級 | 依評級 |
| 來源 | 哪個視角或事故發現的 |
| 緩解方案 | 可排入 backlog 的具體工作：設計變更、監控、演練或流程 |
| 緩解後等級 | 驗證緩解是否有效 |
| 負責人、狀態 | Open、Mitigating、Accepted、Closed |

## 高風險閉環

等級為高的風險必須逐項以下列方式之一處理，才能放行：

1. **緩解**：設計變更或補償控制，使等級降到中以下。
2. **接受**：由有權者明確簽署接受，記錄理由與觸發重審的條件。
3. **迴避**：改變方案，繞開風險來源。

「先上線再說」是沒有紀錄的接受，事故後無人負責，不是合法的處理方式。重大的緩解或接受決策撰寫 ADR。

## 產出

1. 風險總覽：高、中、低各幾項，加一句總體評語。
2. 風險登錄表。
3. 高風險的閉環紀錄：處理方式與剩餘風險。
4. 監控與演練清單：哪些風險靠告警或演練持續看守。
