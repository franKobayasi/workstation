# 現有架構盤點

對既有系統做設計或審查，最大的風險是基於錯誤的現況認知做判斷。文件常過時、口述常失真，因此盤點以程式碼與設定為事實來源，並把觀察到的與推測的分開。

## 資訊來源的優先序

| 優先 | 來源 | 可信度 | 注意 |
|---|---|---|---|
| 1 | 程式碼、設定檔、IaC、CI/CD 定義 | 最高 | 費時但最準 |
| 2 | 生產監控、日誌、流量數據 | 高 | 反映真實的依賴與熱點 |
| 3 | 既有的架構文件、ADR、圖 | 中 | 標明文件日期並驗證 |
| 4 | 團隊訪談、使用者口述 | 中 | 用於補充脈絡與歷史原因 |

文件與程式碼衝突時以程式碼為準，並記錄差異；差異本身是重要的發現。

## 結論的標記

每個結論標為下列之一：

| 標記 | 意義 |
|---|---|
| 觀察 | 有程式碼、設定或數據直接支持，附位置 |
| 推斷 | 由多個觀察推導而來，寫出推導鏈 |
| 未知 | 缺乏資訊，列入待確認問題 |

不批評「為什麼當初這樣做」；先假設當時有合理的約束，把疑問放進訪談清單。

## 盤點步驟（有 codebase 時）

1. **快速定向**：讀 README、頂層目錄結構與 build 檔（`package.json`、`pom.xml`、`go.mod` 等），判斷單體或多服務、語言與框架、分層慣例，寫一段標明為待驗證的初步印象。
2. **邊界與進出口**：
   - 入口：HTTP 路由、gRPC service、排程任務、佇列消費者、CLI。
   - 出口：外呼的 HTTP client、資料庫連線、佇列 producer、第三方 SDK 的初始化。
   - 設定：環境變數、feature flag、secret 的引用（只記名稱，不記值）。
3. **內部結構與資料**：模組依賴方向與循環依賴、核心領域模組；主要資料表與關鍵欄位、migration 透露的演進痕跡；Dockerfile、manifest 與 IaC 揭露的實際拓撲。
4. **現況視圖**：依[C4 架構圖](kb:process/4dcc39)產出 L1 與 L2，元素標明證據來源；技術清單（技術、版本、用途、EOL 狀態）；依賴地圖（內部模組與外部系統，含同步或非同步與關鍵程度）。
5. **痛點與債務**：每項附證據位置。
   - 結構性：循環依賴、上帝模組、層間穿透、複製貼上的重複邏輯。
   - 營運性：沒有健康檢查、日誌不足、設定寫死、無法水平擴展的狀態。
   - 演進性：過舊或 EOL 的依賴、核心路徑沒有測試、與文件嚴重不符。

## 只有文件或口述時

- 明確告知分析基於二手資料，可信度受限。
- 產出訪談問題清單，按主題分組：邊界與整合、資料與一致性、部署與維運、歷史決策與事故、已知痛點。
- 每個結論標明來源：哪份文件的哪一段，或誰說的。

## 產出

1. 系統概述：做什麼、多大、什麼技術、什麼形態，3 到 5 句。
2. 現況的 C4 L1 與 L2。
3. 技術清單。
4. 依賴地圖，標明外部依賴的關鍵程度。
5. 痛點與債務清單，附證據。
6. 未知與待確認問題的彙總。
