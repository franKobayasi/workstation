# 技術選型評估

技術選型失敗很少是因為技術本身差，多半是評估方式錯了：被 benchmark 或熱度帶著走、忽略團隊能力與營運成本、沒有驗證就全押。本方法讓選型結論可辯護、可追溯。

## 前置判斷

很多選型到這裡就該結束：

1. **真的需要新技術嗎**：現有技術棧稍加調整能否滿足。每個組織能承擔的新技術數量有限，留給真正的差異化。
2. **組織有既定標準嗎**：有 Tech Radar 或技術標準時先對齊；偏離標準需要更強的理由與更完整的紀錄。
3. **單向門還是雙向門**：雙向門（例如更換 log library）輕量評估、快速試；單向門（主資料庫、核心訊息協定、雲供應商）依[重大技術決策的規則](kb:process/8b58b1)。

## 準則與權重

先定準則與權重，再看選項；順序顛倒會不自覺地為心中的答案湊分。從下列維度挑 5 到 9 個，並與利害關係人確認權重：

| 維度 | 評估問題 |
|---|---|
| 功能契合度 | 覆蓋核心需求的程度，缺口需要多少自建 |
| 品質屬性支撐 | 對本案驅動屬性的實證能力 |
| 成熟度與社群 | 版本歷史、維護活躍度、重大 issue 的處理速度、大型生產案例 |
| 團隊能力 | 現有技能的匹配度、學習曲線、招聘市場的供給 |
| 營運成本 | 授權、基礎設施、維運人力與升級成本，以三年計 |
| 生態系與整合 | 與現有技術棧、監控、CI/CD 的整合成熟度 |
| 安全與合規 | 漏洞歷史、修補節奏、認證、資料落地要求 |
| 供應商鎖定 | 退出成本、是否有開放標準或替代品 |
| 文件與支援 | 官方文件品質、商業支援選項 |

權重用 1 到 5 並固定總和以強迫取捨，或標為 Critical、Important、Nice-to-have。

## 候選清單

- 3 到 5 個候選，必含一個保守選項（現有技術或最主流的方案）作為基準線。
- 每個候選先寫 2 到 3 句客觀描述：定位、授權模式、代表性的使用者。
- 使用者只指定兩個候選時，確認是否有被忽略的第三個選項，包括維持現狀。

## 加權評分矩陣

| 準則（權重） | 候選 A | 候選 B |
|---|---|---|
| 功能契合（5） | 4 → 20 | 5 → 25 |
| 團隊能力（4） | 5 → 20 | 2 → 8 |
| **加權總分** | **xx** | **xx** |

- 每格分數（1 到 5）附一句證據與來源（官方文件、實測、案例）；沒有證據標「推測」。
- 總分差距小於 10% 視為平手，改由風險與可逆性判斷。
- 矩陣是溝通與檢查的工具，不是決策機器；結果違反直覺時，先檢查是否漏了準則。

## PoC

分數接近或風險高時必須做 PoC，並針對最不確定的假設設計：

```markdown
## PoC 計畫：{候選技術}
- 要回答的問題（1 到 3 個），例如「在 5k RPS 下 P99 延遲是否 < 50ms」
- Timebox：X 人日，超時即停，超時本身就是資訊
- 成功標準：可量化的門檻
- 淘汰條件：出現什麼結果直接出局
- 環境與資料：盡量貼近生產的資料量級與併發模式
- 不驗證的範圍：明確排除，避免 PoC 膨脹
```

## 評估報告

1. 結論與建議：推薦誰、為什麼、代價是什麼。
2. 評估準則與權重，含利害關係人的確認紀錄。
3. 加權評分矩陣，含每格的證據。
4. PoC 結果摘要。
5. 推薦方案的前三大風險與緩解方式。
6. 落選方案，各一句落選理由。
7. 建議的下一步，例如撰寫 ADR。

## 反模式

- 因為新、熱門、大會在講就選它。
- 只看官方跑分，不看自己的工作負載特徵。
- 只算進場成本，不算三年後想換的代價。
- 先有答案再調權重；防範方式是權重先公開確認再評分。
- 把驗證用的 PoC 程式碼直接上線。
